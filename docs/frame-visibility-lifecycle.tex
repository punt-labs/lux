% ============================================================
\section{Introduction}
% ============================================================

Two different authorities write to the same frame.  A \emph{client} writes
its content --- \texttt{show()} installs a scene, \texttt{update()} replaces
one, an empty push or a manifest purge takes one away, and the owner of a
frame ends it when asked.  The \emph{user} writes its visibility --- the
minimize button docks a frame, and a dock pill, the Windows menu or the frame's
menu entry brings it back.  DES-065's R8 states the rule these two must obey:
an agent's push is a notification, not a window-raise.  DES-088 generalises it
to the whole of the lifecycle:

\begin{quote}
  A content event never writes visibility; a visibility event never writes
  content.
\end{quote}

DES-103 decision 6 settles the controls.  Every frame has \textbf{--}, which
minimizes it to the dock bar with all state kept.  A frame whose owner
registered an end handler also has \textbf{$\times$}, which asks the owner to
end the content; the owner does so, and the frame goes with its last scene.
Visibility has two values, on screen and docked.  There is no third state in
which a frame is hidden without a pill, and so no way for a client to reopen a
frame the user shut.

This document models the two axes as independent state, adds the end handler
as a per-frame client capability, and states the separation as invariants, so
that ProB can enumerate the reachable states and either confirm the separation
holds or produce the exact offending trace.

% ============================================================
\section{Basic Types}
% ============================================================

\begin{zed}
  [FRAME, SCENE]
\end{zed}

\texttt{FRAME} is the set of frame identifiers a client may name;
\texttt{SCENE} the set of scene identifiers.  Both carriers are bounded by
ProB's \texttt{DEFAULT\_SETSIZE}, so no explicit cardinality constant is
needed.  Two of each suffice: one frame that is minimized or ended and one
bystander, one scene that is pushed again and one that arrives new.

% ============================================================
\section{Free Types}
% ============================================================

\begin{zed}
  VIS ::= vOnScreen | vDocked
\end{zed}

A frame's visibility, and the whole of it.  \texttt{vOnScreen}: painted as an
inner window.  \texttt{vDocked}: not painted, carrying a dock pill.  Both are
reversible by the user without the client's help.

% ============================================================
\section{State}
% ============================================================

The state is flat: one schema, eleven components.  Four are the Display's
replica of client-owned content, one is the client's end-handler registration
together with the Display's record of an end request in flight, two are the
Display-owned visibility and focus, and the rest are ghosts --- history
variables that record what the \emph{user} did, or what a content event did,
so that a later state can be judged against it.  The ghosts are a modelling
device with no counterpart in the code, and they are named where they appear.

\begin{schema}{Sys}
  frames : \power FRAME \\
  content : \power SCENE \\
  sceneFrame : SCENE \pfun FRAME \\
  vis : FRAME \pfun VIS \\
  activeTab : FRAME \pfun SCENE \\
  focus : \power FRAME \\
  handler : \power FRAME \\
  endPending : \power FRAME \\
  userDocked : \power FRAME \\
  autoFocused : \power FRAME \\
  tabStolen : \power FRAME
\where
  \dom vis = frames \\
  \dom activeTab = frames \\
  \dom sceneFrame = content \\
  \ran sceneFrame \subseteq frames \\
  \forall f : frames @ f \in \ran sceneFrame \\
  \forall f : frames @ activeTab~f \in content \\
  \forall f : frames @ sceneFrame~(activeTab~f) = f \\
  focus \subseteq frames \\
  \# focus \leq 1 \\
  handler \subseteq frames \\
  endPending \subseteq frames
\end{schema}

\texttt{content} is the set of scene ids the replica holds --- exactly the
domain of \texttt{sceneFrame}, since every scene lives in a frame.  Membership
of \texttt{content} is what the code computes as \texttt{is\_new}: a scene id
outside it is \emph{unseen}, one inside it is \emph{known}.

\texttt{focus} is the one-shot focus request the renderer consumes, modelled
as a set of size at most one so the empty set can stand for ``none'' without
a sentinel.

\texttt{handler} is the set of frames whose owner registered an end handler.
It is the whole of the Display's knowledge of which frames can be ended, and
the only thing that makes \textbf{$\times$} appear.  \texttt{endPending} is
the set of frames for which the Display has routed a \textbf{$\times$} to the
owner, through the remote-dispatch path of D21, and has not yet seen the
owner end them.  The owner is a separate process: the request and its answer
are two events, and the frame is on screen or docked, with all its content,
between them.

\texttt{userDocked} is the ghost recording that the user's latest visibility
decision for a frame was to dock it.  It is written by the visibility
operations only, and cleared by a restore or by the frame's removal.

The predicate carries only \emph{structural} invariants: the coverage of the
three partial functions, the no-husk rule (every frame holds at least one
scene, which is why a frame and its content appear and disappear together),
the active tab pointing at a scene of its own frame, the cardinality of the
focus request, and the registration and the request each naming an existing
frame.  These hold in every design, correct or broken, so they act as
coherence constraints rather than as the properties under test.  The safety
properties (Section~\ref{sec:inv}) are deliberately \emph{absent} here: a
predicate placed in \texttt{Sys} is enforced as a guard on every successor
state, which would silently disable any operation that broke it and mask the
very defects this model exists to catch.

% ============================================================
\section{Content Operations}
% ============================================================

The operations a client can cause.  Together they are the whole of
\texttt{SceneReplica.handle\_framed\_scene} and of the owner's answer to an
end request.  Not one of them writes the \texttt{vis} of a frame that already
exists, \texttt{focus}, or the \texttt{activeTab} of a frame that already has
one --- that is the R8 rule, and stating it operation by operation is what
makes it checkable.  The two removals delete a frame's own entry from
\texttt{vis}, which is the end of that frame and not a write to it.

% -------------------------------------------------------------------
\subsection{Push a New Scene into a New Frame}
% -------------------------------------------------------------------

An unseen scene naming a frame that does not exist yet.  This is the one
place a content event sets a visibility value, and it is sound precisely
because there is no prior value to override: a frame is born
\texttt{vOnScreen}.  That choice is the \emph{Display's} new-frame policy, not
something the Hub forces.  Being born on screen is not a raise: no focus is
requested, no other frame is disturbed, and the Display window's own
shown/hidden state (R1) is untouched.  A new frame has no end handler until
its owner registers one.

\begin{schema}{PushNewFrame}
  \Delta Sys \\
  s? : SCENE \\
  f? : FRAME
\where
  s? \notin content \\
  f? \notin frames \\
  frames' = frames \cup \{ f? \} \\
  content' = content \cup \{ s? \} \\
  sceneFrame' = sceneFrame \cup \{ s? \mapsto f? \} \\
  vis' = vis \cup \{ f? \mapsto vOnScreen \} \\
  activeTab' = activeTab \cup \{ f? \mapsto s? \} \\
  focus' = focus \\
  handler' = handler \\
  endPending' = endPending \\
  userDocked' = userDocked \\
  autoFocused' = autoFocused \\
  tabStolen' = tabStolen
\end{schema}

% -------------------------------------------------------------------
\subsection{Push a New Scene into an Existing Frame}
% -------------------------------------------------------------------

An unseen scene joining a frame that is already there --- a second tab.  The
frame's visibility is whatever the user last made it, and stays that way; the
new scene joins the tab strip without taking the selection.

\begin{schema}{PushNewScene}
  \Delta Sys \\
  s? : SCENE \\
  f? : FRAME
\where
  s? \notin content \\
  f? \in frames \\
  content' = content \cup \{ s? \} \\
  sceneFrame' = sceneFrame \cup \{ s? \mapsto f? \} \\
  frames' = frames \\
  vis' = vis \\
  activeTab' = activeTab \\
  focus' = focus \\
  handler' = handler \\
  endPending' = endPending \\
  userDocked' = userDocked \\
  autoFocused' = autoFocused \\
  tabStolen' = tabStolen
\end{schema}

% -------------------------------------------------------------------
\subsection{Push a Scene Already Held}
% -------------------------------------------------------------------

The repaint: \texttt{update()}, a beads reload, a track change.  It replaces
element content the Display renders, which this model does not carry, and it
changes nothing else at all.  The $\Xi$ says the whole rule.

\begin{schema}{PushRepeat}
  \Xi Sys \\
  s? : SCENE
\where
  s? \in content
\end{schema}

A scene moving from one frame to another --- the branch of
\texttt{upsert\_scene\_in\_frame} that dismisses a scene from its old frame
first --- is deliberately not modelled.  It is a content-to-content
relocation with no visibility consequence, and adding it would grow the state
space without touching the properties under test.

% -------------------------------------------------------------------
\subsection{Dispose a Scene}
% -------------------------------------------------------------------

The one way ``known'' is legitimately lost, other than an owner's end: an
empty push, a Hub manifest that disowns the scene, or a frame TTL that has
passed.  The client is saying the content is gone, and after it the id is
genuinely unseen again.

When other scenes remain in the frame, the frame stays and the active tab
falls back to a survivor, named by \texttt{keep?}.  The end handler and any
request in flight belong to the frame and are untouched.

\begin{schema}{DisposeScene}
  \Delta Sys \\
  s? : SCENE \\
  f? : FRAME \\
  keep? : SCENE
\where
  s? \in content \\
  sceneFrame~s? = f? \\
  keep? \in \dom (sceneFrame \rres \{ f? \}) \\
  keep? \neq s? \\
  content' = content \setminus \{ s? \} \\
  sceneFrame' = \{ s? \} \ndres sceneFrame \\
  activeTab' = activeTab \oplus \{ f? \mapsto keep? \} \\
  frames' = frames \\
  vis' = vis \\
  focus' = focus \\
  handler' = handler \\
  endPending' = endPending \\
  userDocked' = userDocked \\
  autoFocused' = autoFocused \\
  tabStolen' = tabStolen
\end{schema}

When the disposed scene was the frame's last, the frame goes with it --- a
frame with no content is a husk, and that holds however the user had left it,
so a \emph{docked} frame whose content is disposed is disposed too.  The frame
id is released from the handler registration, the request and the ghosts
along with everything else: the next arrival under that id is a genuinely new
frame with no end handler.

\begin{schema}{DisposeFrame}
  \Delta Sys \\
  s? : SCENE \\
  f? : FRAME
\where
  s? \in content \\
  sceneFrame~s? = f? \\
  \dom (sceneFrame \rres \{ f? \}) = \{ s? \} \\
  content' = content \setminus \{ s? \} \\
  sceneFrame' = \{ s? \} \ndres sceneFrame \\
  frames' = frames \setminus \{ f? \} \\
  vis' = \{ f? \} \ndres vis \\
  activeTab' = \{ f? \} \ndres activeTab \\
  focus' = focus \setminus \{ f? \} \\
  handler' = handler \setminus \{ f? \} \\
  endPending' = endPending \setminus \{ f? \} \\
  userDocked' = userDocked \setminus \{ f? \} \\
  autoFocused' = autoFocused \setminus \{ f? \} \\
  tabStolen' = tabStolen \setminus \{ f? \}
\end{schema}

% -------------------------------------------------------------------
\subsection{Register an End Handler}
% -------------------------------------------------------------------

The client declares that a frame's content can be ended.  It is a statement
about the frame's owner, not a visibility value: it writes \texttt{handler}
and nothing else, so a client cannot dock, undock, focus or raise a frame by
registering.  The frame must exist; a registration for a frame that has not
been pushed is not an operation of this model.

\begin{schema}{RegisterEndHandler}
  \Delta Sys \\
  f? : FRAME
\where
  f? \in frames \\
  f? \notin handler \\
  handler' = handler \cup \{ f? \} \\
  frames' = frames \\
  content' = content \\
  sceneFrame' = sceneFrame \\
  vis' = vis \\
  activeTab' = activeTab \\
  focus' = focus \\
  endPending' = endPending \\
  userDocked' = userDocked \\
  autoFocused' = autoFocused \\
  tabStolen' = tabStolen
\end{schema}

% -------------------------------------------------------------------
\subsection{The Owner Ends the Content}
% -------------------------------------------------------------------

The owner, having received the Display's request, ends the frame's content:
for a terminal, the shell exits and every scene of the frame is disposed.  It
is a content event, and its effect is the removal of the frame --- the
no-husk rule applied to a frame whose scenes all go at once.  It writes the
visibility and focus of no other frame.  It is enabled only for a frame with
a request in flight: the owner answers a request, and a frame whose end was
never asked for is not ended by this operation.

\begin{schema}{OwnerEnd}
  \Delta Sys \\
  f? : FRAME
\where
  f? \in endPending \\
  content' = content \setminus \dom (sceneFrame \rres \{ f? \}) \\
  sceneFrame' = \dom (sceneFrame \rres \{ f? \}) \ndres sceneFrame \\
  frames' = frames \setminus \{ f? \} \\
  vis' = \{ f? \} \ndres vis \\
  activeTab' = \{ f? \} \ndres activeTab \\
  focus' = focus \setminus \{ f? \} \\
  handler' = handler \setminus \{ f? \} \\
  endPending' = endPending \setminus \{ f? \} \\
  userDocked' = userDocked \setminus \{ f? \} \\
  autoFocused' = autoFocused \setminus \{ f? \} \\
  tabStolen' = tabStolen \setminus \{ f? \}
\end{schema}

% ============================================================
\section{Visibility Operations}
% ============================================================

The operations a user can cause.  Not one of them writes \texttt{content} or
\texttt{sceneFrame}: putting a window away is not throwing its contents out,
and asking for it to be ended is not ending it.

% -------------------------------------------------------------------
\subsection{Minimize}
% -------------------------------------------------------------------

The user clicks \textbf{--}.  Every frame has it.  The frame keeps all its
state and gains a dock pill; \texttt{userDocked} records that the user did it.

\begin{schema}{Minimize}
  \Delta Sys \\
  f? : FRAME
\where
  f? \in frames \\
  vis~f? = vOnScreen \\
  vis' = vis \oplus \{ f? \mapsto vDocked \} \\
  focus' = focus \setminus \{ f? \} \\
  userDocked' = userDocked \cup \{ f? \} \\
  frames' = frames \\
  content' = content \\
  sceneFrame' = sceneFrame \\
  activeTab' = activeTab \\
  handler' = handler \\
  endPending' = endPending \\
  autoFocused' = autoFocused \\
  tabStolen' = tabStolen
\end{schema}

% -------------------------------------------------------------------
\subsection{Set the Dock State}
% -------------------------------------------------------------------

A client adjusting a frame's dock state through \texttt{set\_frame\_state} ---
the operation the whole client surface carries (MCP, REST, CLI), and the one
Collapse All and Expand All reduce to.  Either value may be set on any frame,
because both are values the user can reverse with a click: with no third state
there is no frame the call could reopen against the user's will, and the guard
that excluded one is gone.

\begin{schema}{SetDockState}
  \Delta Sys \\
  f? : FRAME \\
  v? : VIS
\where
  f? \in frames \\
  vis' = vis \oplus \{ f? \mapsto v? \} \\
  v? = vDocked \implies userDocked' = userDocked \cup \{ f? \} \\
  v? = vOnScreen \implies userDocked' = userDocked \setminus \{ f? \} \\
  frames' = frames \\
  content' = content \\
  sceneFrame' = sceneFrame \\
  activeTab' = activeTab \\
  focus' = focus \\
  handler' = handler \\
  endPending' = endPending \\
  autoFocused' = autoFocused \\
  tabStolen' = tabStolen
\end{schema}

It leaves \texttt{focus} alone rather than clearing it, matching the code: only
a minimize releases a pending focus request, and a bulk dock does not.

% -------------------------------------------------------------------
\subsection{Raise}
% -------------------------------------------------------------------

The whole gesture behind a user asking for a frame by name: an applet's menu
entry click (DES-063's raise-first pattern), a dock pill, Expand All, the
Windows menu.  Restoring and focusing are one operation, not two.  It is
enabled from either visibility, and it is the only operation that both puts a
frame on screen and takes focus.

\begin{schema}{Raise}
  \Delta Sys \\
  f? : FRAME
\where
  f? \in frames \\
  vis' = vis \oplus \{ f? \mapsto vOnScreen \} \\
  focus' = \{ f? \} \\
  userDocked' = userDocked \setminus \{ f? \} \\
  frames' = frames \\
  content' = content \\
  sceneFrame' = sceneFrame \\
  activeTab' = activeTab \\
  handler' = handler \\
  endPending' = endPending \\
  autoFocused' = autoFocused \\
  tabStolen' = tabStolen
\end{schema}

% -------------------------------------------------------------------
\subsection{End}
% -------------------------------------------------------------------

The user clicks $\times$ and confirms.  The control is on screen only when the
frame's owner registered an end handler, so the operation requires one; and it
is on the title bar of a painted frame, so the frame is on screen.  The
Display routes the request to the owner and changes nothing else: the frame
stays where it is, with all its content, until the owner answers with
\texttt{OwnerEnd}.  An owner that never answers leaves a frame the user can
still minimize, raise or ask again about.  The $\times$ is a visibility-axis
event, and so it writes no content.

\begin{schema}{End}
  \Delta Sys \\
  f? : FRAME
\where
  f? \in frames \\
  f? \in handler \\
  vis~f? = vOnScreen \\
  endPending' = endPending \cup \{ f? \} \\
  frames' = frames \\
  content' = content \\
  sceneFrame' = sceneFrame \\
  vis' = vis \\
  activeTab' = activeTab \\
  focus' = focus \\
  handler' = handler \\
  userDocked' = userDocked \\
  autoFocused' = autoFocused \\
  tabStolen' = tabStolen
\end{schema}

\section{Invariants}
\label{sec:inv}
% ============================================================

Five properties must hold across every reachable state.  The first four are
state predicates; the fifth is a property of the transition relation.  None
is placed in \texttt{Sys}, for the reason given with that schema.

\paragraph{Invariant 1 --- content never takes focus.}
No focus request is ever raised by a content event:
\[
  autoFocused = \emptyset.
\]
The ghost is written by no operation in this specification, so the property is
established by construction here and is a \emph{reachability} question only in
a fidelity variant, where a push or an owner's end writes it.  This is
criterion R8 in its narrowest form: \texttt{show()} and \texttt{update()}
never raise, whether or not the scene is new.

\paragraph{Invariant 2 --- content never steals the tab.}
No active-tab change is ever caused by a content arrival:
\[
  tabStolen = \emptyset.
\]
The active tab is a user-owned selection, in the same category as visibility.
A new scene may join a frame's tab strip; it may not pull the selection off
whatever the user was reading.  \texttt{DisposeScene} does repoint the tab,
but only away from a scene that has ceased to exist and only to a survivor,
which is a repair, not a steal.

\paragraph{Invariant 3 --- content never undocks a frame.}
No frame is on screen while the user's latest decision for it stands as
docked:
\[
  \{ f : frames | f \in userDocked \land vis~f = vOnScreen \} = \emptyset.
\]
This is the surviving half of DES-088's bug B, stated as a property: a
background push, and now an owner's end of some other frame, must not bring
back a window the user put away.  \texttt{Raise} and \texttt{SetDockState}
are the only operations that set \texttt{vOnScreen} on an existing frame, and
each clears \texttt{userDocked} in the same step.

\paragraph{Invariant 4 --- $\times$ needs a handler.}
A request to end a frame's content exists only for a frame whose owner
registered an end handler:
\[
  endPending \subseteq handler.
\]
This is the DES-103 rule that $\times$ ``appears only on a frame whose owner
can end its content'', stated on the state the Display holds.  Any state
where it fails is an end request routed to an owner that never said it could
end anything.

\paragraph{Invariant 5 --- deadlock freedom.}
No reachable state leaves every operation disabled.  \texttt{DisposeFrame}
and \texttt{OwnerEnd} return a frame id and its scene ids to their unseen
pools, so a workspace can always be emptied and repopulated and the system
cycles rather than terminating; and \texttt{PushNewFrame} is enabled in the
empty state.  This is a property of the reachable state space, discharged by
the model check in Section~\ref{sec:verify} rather than by a goal.

That $\times$ writes no content, and that \texttt{OwnerEnd} is enabled only
after a request, are properties of single operations and are checked as
deterministic trace replays (Section~\ref{sec:fidelity}), not as goals.

\section{Verification}
\label{sec:verify}
% ============================================================

Type-checking is a \texttt{fuzz} pass:
\begin{verbatim}
  fuzz -t docs/frame-visibility-lifecycle.tex
\end{verbatim}

Invariants 1 to 4 are state properties, checked by asking ProB whether the
\emph{negation} of each is reachable.  A goal that is not found means the
invariant holds on every reachable state:
\begin{verbatim}
  # Invariant 1
  probcli docs/frame-visibility-lifecycle.tex -model_check -nodead \
    -goal "autoFocused /= {}" -p DEFAULT_SETSIZE 2

  # Invariant 2
  probcli docs/frame-visibility-lifecycle.tex -model_check -nodead \
    -goal "tabStolen /= {}" -p DEFAULT_SETSIZE 2

  # Invariant 3
  probcli docs/frame-visibility-lifecycle.tex -model_check -nodead \
    -goal "card({f|f:FRAME & f:frames & f:userDocked & vis(f)=vOnScreen})>0" \
    -p DEFAULT_SETSIZE 2

  # Invariant 4
  probcli docs/frame-visibility-lifecycle.tex -model_check -nodead \
    -goal "not(endPending <: handler)" -p DEFAULT_SETSIZE 2
\end{verbatim}

A goal predicate may not name an element of a given set: \texttt{probcli}
rejects \texttt{FRAME2 : frames} with a \texttt{type\_expression\_error}
even though it prints those names in its own traces, and the model-check then
reports ``no counter example'' \emph{vacuously}.  Every goal above is therefore
written over the state components and bound variables only.

Invariant~5 is the deadlock check over the full reachable state space, which
is what \texttt{-model\_check} performs when no \texttt{-nodead} is given:
\begin{verbatim}
  probcli docs/frame-visibility-lifecycle.tex -model_check \
    -p DEFAULT_SETSIZE 2
\end{verbatim}

\paragraph{\texttt{-cbc\_deadlock} reports a spurious deadlock here, and on
every other Z specification in this repository.  Ignore it.}
In ProB's Z mode \texttt{-cbc\_deadlock} does not constrain its solutions to
the state schema, so the state it reports is not a state of this
specification: it violates \texttt{Sys}'s own predicate.  The reachable-state
check above is the authoritative one, and its deadlock detection is live
rather than vacuous.

\section{Fidelity}
\label{sec:fidelity}
% ============================================================

A model that cannot reproduce the defects it guards against proves nothing.
Each variant below is this specification with one operation changed to the
behaviour a plausible implementation would have, and each must reach the
state the corresponding invariant forbids.

\begin{center}
\begin{tabular}{lll}
  \textbf{Variant} & \textbf{Change} & \textbf{Goal found} \\
  \hline
  \texttt{push-arrival} & \texttt{PushNewFrame} and \texttt{PushNewScene}
    carry the old \texttt{is\_new} side effect: raise the frame,
    request focus, take the tab & 1, 2, 3 \\
  \texttt{end-no-handler} & \texttt{End} does not require
    \texttt{f? $\in$ handler} & 4 \\
  \texttt{end-writes-visibility} & \texttt{OwnerEnd} also puts every
    surviving frame on screen & 3 \\
\end{tabular}
\end{center}

\paragraph{\texttt{push-arrival}.}  This is today's pre-DES-088 behaviour,
kept as the control for the content-never-writes-visibility rule: a content
event that clears the dock, requests focus and takes the tab.  It reaches the
focus steal, the tab steal and the reopened frame.

\paragraph{\texttt{end-no-handler}.}  The $\times$ available on a frame whose
owner never said it could end anything.  \texttt{PushNewFrame} followed by
\texttt{End} puts the frame in \texttt{endPending} with \texttt{handler}
empty: ProB reaches the negation of invariant~4, and two steps are enough
(its own witness is longer and varies between runs).  In the intact
model the same sequence is refused at step 2, because \texttt{End}'s guard
$f? \in handler$ is false.

\paragraph{\texttt{end-writes-visibility}.}  Ending content writing
visibility: when the owner ends one frame, the Display brings every other
frame back on screen.  With one frame docked by the user and another ended,
the docked frame is on screen while \texttt{userDocked} still holds it ---
the negation of invariant~3, reached without a push of any kind.  This is the
DES-088 rule applied to the new event: ending is content, and content does
not write visibility.

\paragraph{Replays.}  Two properties are properties of one operation, and a
trace replay with \texttt{probcli -t} states each deterministically.  The
script runs both.

\begin{verbatim}
  machine('frame-visibility-lifecycle').
  '$initialise_machine'.
  'PushNewFrame'(fd(1,'FRAME'),fd(1,'SCENE')).
  'RegisterEndHandler'(fd(1,'FRAME')).
  'End'(fd(1,'FRAME')).
  'OwnerEnd'(fd(1,'FRAME')).
\end{verbatim}

\noindent
This replays: the frame survives \texttt{End} with its content, and is removed
only by \texttt{OwnerEnd}.  Dropping the \texttt{RegisterEndHandler} step makes
the replay fail at \texttt{End}; dropping the \texttt{End} step makes it fail at
\texttt{OwnerEnd}, so the owner cannot end a frame nobody asked it to.

\section{What this model does not carry}
% ============================================================

Four things are deliberately out of scope, and are named so that a reader
does not mistake silence for a claim.

\begin{itemize}
  \item \textbf{The Display window's own shown/hidden state} (R1 of the same
    epic).  This model is about frames \emph{within} the workspace.  The rule
    it establishes --- a content event never changes visibility --- is the
    same rule R1 applies one level up, and nothing here contradicts it: a
    frame born \texttt{vOnScreen} inside a hidden window is still invisible.
  \item \textbf{Persistence across a Display restart.}  \texttt{vDocked}, like
    focus and cascade position, is Display-local session state; a restarted
    Display rebuilds its replica from the Hub's manifest and every frame is
    created fresh, with the end handlers its owners register again.
  \item \textbf{The confirm, and the owner declining.}  The confirm dialog
    is the user's, and a cancelled one is no event.  An owner that answers a
    request by keeping its content changes no state this model holds, so it
    is not an operation here; the frame stays with its request in flight and
    \texttt{End} may be repeated.
  \item \textbf{Scene content and element identity.}  A push carries an
    element tree, and replacing one retires the element ids it dropped.  That
    is modelled in \texttt{docs/patch\_application.tex} and is orthogonal to
    visibility.
\end{itemize}
